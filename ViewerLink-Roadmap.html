Viewer Link — roadmap

A second phone reviews runs while the recording phone stays untouched on its tripod. Phase 1 ships that. Phase 2 is next: it makes the viewing phone the real app rather than a web page, which is the only thing that changes what a coach can actually do with a clip.

Source of truth for Phase 1's contract and security model: ViewerLink-Phase1-Spec.md — this page summarises §3 and the decisions that shape what comes after.

Phase 1 — browser viewer

Shipped

The recorder serves, the viewer uses a web browser.

  • A read-only HTTP server on the recorder, five endpoints. Every push-based transfer needs a tap on the sending device, so the recorder listens and the viewer drives.
  • No app install on the viewer — it is a web page, so an iPhone or a borrowed phone works. This is the main reason Phase 1 is a page and not a second app mode.
  • Settings › Viewer Link turns it on and shows a QR code. The page mirrors the gallery — 9:16 tiles grouped by day, time, duration, import tag — and polls every 5s, so a run recorded after it is open appears on its own.
  • A foreground service keeps the socket alive once the recorder's screen goes off, with a Stop action in the notification.

Both phones must already be on the same network. You turn the phone's hotspot on yourself before mounting the tripod — a one-time step before the phone is mounted, so it does not violate "don't touch the recorder". Automating it was considered and parked; see below.

Phase 2 — native viewer mode

Next

The viewing phone stops being a web page and becomes the real app.

  • Remote clips appear in the actual gallery and VideoPlayerView, which brings the pose overlay, drawing tools and side-by-side comparison to the viewer. The web page has plain playback only — the overlay and drawing are exactly what Phase 2 buys.
  • Server-sent events, so a new clip appears the instant it is saved instead of up to 5s later.

The cleartext obstacle is settled: media3's stock HTTP stack is refused by the cleartext policy, and a network security config cannot name "any private address" (no CIDR, and hotspot subnets move). So the viewer talks to the recorder over a raw socket, which the policy does not govern: ViewerHttpClient + RemoteClipDataSource, with an instrumented test that plays and seeks a clip under the release policy. The shipped app keeps the strict default.

Plan: stream to play, download to analyse (the pose overlay reads frames from a cached file), and a ClipRef model so local and remote clips can be compared side by side. Five milestones, the first of which touches only the gallery's MediaStore query. See ViewerLink-Phase2-Spec.md.

Phase 3 — control channel

Later

The viewer stops being read-only.

  • Arm and disarm Auto, trigger a recording, change duration — all from the viewer.

This is the first phase that adds a write path, which puts two deliberate Phase 1 decisions up for review: the plain-HTTP-plus-token security model, and the hand-rolled HTTP server (the spec suggests considering Ktor CIO at that point).

Phase 1.5 — app-provisioned hotspot

Parked

Considered, and not worth what it costs.

The idea was startLocalOnlyHotspot with the SSID and passphrase in the QR, so the viewer joins by scanning instead of picking the hotspot and typing a passphrase.

  • It cannot deliver the "one scan" it was sold on. A QR carries one payload and the scanner dispatches on its scheme: WIFI: joins a network, http:// opens a page. There is no field in the Wi-Fi format for a URL, so it is two codes and two scans on every platform. What is left is a saved passphrase entry.
  • Some devices kill a local-only hotspot when the app backgrounds — which attacks the core requirement directly. The recorder sits untouched with its screen off for a whole session; a system hotspot survives that, an app-provisioned one may not, on hardware you cannot enumerate in advance.
  • Some devices require Location to be on; passphrase retrieval differs across API 26/28/30. It is the single biggest source of OEM-specific behaviour in the design.
  • A local-only hotspot has no upstream, so an iPhone viewer shows "no internet connection" and may drift back to cellular. A shared hotspot has none of that — this is cost the manual route does not carry.

There is no cheap half-measure either: the app cannot read the current hotspot's SSID and passphrase to build a join-QR for it, because getWifiApConfiguration() has been restricted since API 26. It is the full local-only hotspot or nothing.

Live camera preview

Not planned

A separate project, not a later phase.

CameraManager.kt already binds Preview + VideoCapture<Recorder> + ImageAnalysis, which is the three-use-case limit on most devices. There is no spare stream to tap for an encoder, and re-encoding from ImageAnalysis would steal frames from the rider detector.

Also permanently out of scope for the viewer: deleting or importing, multi-viewer sync, transcoding, and any cloud path.

Paid for in Phase 1, spent later

Four decisions that only make sense in light of the phases above. Changing any of them without reading this costs a later phase.

Phase 2

Range support is load-bearing

Without it a seek re-downloads the clip, and media3 over http:// could not seek at all. HttpRange is pure and heavily unit-tested — keep it that way.

Phase 2

/api/clips/{id}/meta exists unused

Phase 1's page never calls it. It ships anyway so Phase 2's frame badge does not force an API version bump.

Phase 3

Per-session token, plain HTTP

Generated on every start, passed in the QR query string, then moved into an HttpOnly; SameSite=Lax cookie. Plain HTTP on purpose: a self-signed cert on a local IP trains people to click through browser warnings. Revisit when a write path arrives.

Phase 2

The gallery is deliberately untouched

ClipCatalog repeats the gallery's MediaStore query rather than sharing it, so the viewer cannot regress the gallery. Phase 2 collapses the two.
